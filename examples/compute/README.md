# Owner compute provider proposal

Local source/config proposal only. Official Wrangler 4.141.0 validated and bundled the Worker and built its Docker image locally in dry-run mode. No provider run, deployment or spend has occurred.

The authenticated owner worker calls the internal service binding methods `execute(ownerScope, request)`, `recover(ownerScope, operationId)`, and `cancel(ownerScope, operationId)`. The service selects `OWNER_COMPUTE.idFromName(JSON.stringify([ownerScope, operationId]))` and the container Durable Object reserves the operation in the existing durable receipt journal before executing it. Returned artifact bytes belong in the existing owner workspace. The model cannot choose a namespace name. This worker returns 404 on every HTTP request. A serving-worker service binding is required; this proposal does not edit the shared serving configuration.

`LinuxContainerExecutor` uses native `ctx.container.exec(argv, options)`. Fixed Node builtin filesystem helpers move inputs over JSON stdin and return artifact bytes over stdout; caller text never enters a shell. The Dockerfile uses the official Node image digest resolved from Docker Hub metadata on 2026-10-07. Wrangler resolves the built image to a digest reference in `ctx.container.images.compute`. No packages, SDK shim, environment credentials, outbound intercepts or internet access are added.

The host must reserve and persist operation evidence before issue, and treat an interrupted provider call as uncertain rather than reissue it. Each execution starts fresh and destroys the container on success, failure, cancellation or bounds violation; the durable workspace rehydrates the next operation. This is file recovery, not process resume. One instance belongs to one owner; Linux user IDs do not create tenant isolation under the provider's `durable_object` scheduling policy.

Limits: total inputs 256 KiB, one output artifact at most 256 KiB, combined command stdout/stderr 16 KiB, complete operation deadline at most 30 seconds. Native startup explicitly chooses `instance: 'lite'` (1/16 vCPU, 256 MiB memory, 2 GB disk). Before issuing code, the container DO persists an alarm for 35 seconds later; the alarm persists cancellation and destroys the VM. Linux code cannot change that DO alarm. The alarm is cleared only after successful executor cleanup; errors leave it available for a cleanup retry. The finite `sleep 35` entrypoint is a secondary guard against ordinary abandoned work after eviction. The supplied argv is general purpose and can access the whole isolated VM. File paths describe relative workspace locations, not an OS security boundary. No network binding or outbound handler is provided. Complete cleanup uses container destruction because individual process termination does not stop descendants.

Provider proof requires compatible current Workers types and Wrangler, Docker for local container execution, and a reviewed provider deployment/spend authorization. The repository currently pins Wrangler 4.135.0; official managed-image local examples require at least 4.141.0. This proposal changes no dependencies or deployment configuration in the serving worker. `local-journey.ts` uses real local Docker Linux with disabled networking and bounded processes; owner directory/R2/channel delivery remain fixtures. That proves a local executable journey, not Cloudflare VM isolation or provider egress enforcement.

Validated local commands (run from repository root except the dry-run):

```sh
pnpm --filter @waldo/runtime exec tsc --noEmit --project tsconfig.compute-example.json
pnpm --filter @waldo/runtime exec vitest run --config vitest.compute-provider.config.ts
cd examples/compute
WRANGLER_SEND_METRICS=false WRANGLER_LOG_PATH=/tmp/waldo-compute-wrangler.log npm exec --yes --cache /tmp/waldo-compute-npm-cache --registry=https://registry.npmjs.org --package=wrangler@4.141.0 -- wrangler deploy --dry-run --config wrangler.jsonc --outdir /tmp/waldo-compute-dry-run
```

The final dry-run exited successfully with `OwnerComputeContainer (durable_object)` and the `OWNER_COMPUTE` namespace binding, a 15.00 KiB Worker bundle, and a successful local Docker build. Its temporary image tag was removed by Wrangler. The provider boundary suite passed 9 tests; the proposal Worker typechecked. The private RPC/alarm paths have source and typecheck proof, not a Cloudflare execution receipt.

Activation requires a reviewed staging deployment of this separate Worker, its SQLite-backed `OWNER_COMPUTE` Durable Object namespace and Container application, and the built image in Cloudflare's managed registry. The serving configuration needs `services: [{ binding: 'COMPUTE', service: 'waldo-owner-compute-proposal' }]`; its adapter must continue deriving `ownerScope` from authenticated canonical owner identity. The service has no public route, workers.dev or preview URL, no outbound intercept, no secrets, and no new R2 or database binding. Existing owner workspace and channel delivery bindings remain their respective authorities. Wrangler's published 4.141.0 source names `workers_scripts:write` for scripts/Durable Objects and `containers:write` for Container management; registry image publication also needs the deployment identity's existing managed-registry write authority. This proposal grants none of them. An exact-owner, one-operation staging activation requires separate deployment/spend authorization.

The `durable_object` policy explicitly rejects `max_instances` and application-level `instance_type`; named image configuration is validated, while the instance size is selected in code. No unsupported fleet cap is claimed or inserted. Existing account limits remain the provider's concurrency ceiling; this proposal supplies no new global spending authorization. See [scheduling policy](https://developers.cloudflare.com/containers/configuration/scheduling-policy/) and [Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/#containers).

At published marginal rates, full utilization of one lite instance for 35 seconds costs $0.000070525: CPU $0.00004375, memory $0.000021875, disk $0.0000049. This is an estimate, not a guaranteed billing ceiling. The API promises `destroy()` resolves after destruction but does not document its precise shutdown latency; the general lifecycle allows up to 900 seconds before forced shutdown. Conservatively pricing 935 seconds gives $0.001884025 in Container CPU/memory/disk, plus unknown startup/alarm delivery overhead. Workers, DO requests/duration/storage, managed-registry storage, existing R2/artifact retention and channel costs are separate; the Workers Paid plan is $5/month and includes usage allowances. No internet egress is allowed. Normal PID1 exit stops the instance, but arbitrary code has root capabilities under this policy and can interfere with Linux-side timers, so the independent persisted DO alarm and platform cleanup remain necessary. See [pricing](https://developers.cloudflare.com/containers/platform/pricing/) and [lifecycle](https://developers.cloudflare.com/containers/concepts/architecture/). An enforceable provider-wide dollar ceiling is not established by this source proposal.
