# Google Workspace capability and release evidence, 2026-09-26

Source snapshot: Waldo `51c9f2fe268e37e225c93c9678f0a57cdb838151` on `beta-mvp`. This is a **source and public-documentation audit**, not a staging test. The [acceptance ledger, issue #177](https://github.com/waldoco/waldo-backend/issues/177) supplies the older live results; its later comments record PR #197 and #183 as merged but not redeployed or newly live-proven. Recheck the release SHA, staging config, and acceptance IDs before changing any status below.

## Decision

Waldo has a narrow owner-bound Google connector for the primary Calendar, primary Gmail inbox metadata/snippets, Gmail draft/send proposals, and default Google Tasks list. It does **not** have general Google Workspace parity. The most urgent gap is internal wiring, not a new scope: `get_tasks`, approved `send_email`, and its send reconciliation refer to methods that the signed Supabase proxy refuses or does not expose. A successful OAuth grant and green source tests cannot establish these actions. [Waldo Google tool handlers](../../../packages/runtime/src/tools/live/google.ts#L59-L155), [Google client interface](../../../packages/runtime/src/connectors/google.ts#L130-L142), [Worker proxy methods](../../../packages/runtime/src/connectors/connections.ts#L14), [Edge proxy methods](../../../supabase/functions/connector-proxy/index.ts#L7-L8).

Two plausible explanations for an absent Tasks result are a model/tool-choice miss and a proxy method failure. A direct synthetic call through the proxy-backed `GoogleAccess.client('tasks')` falsifies the first; the current `METHODS` omissions establish that this path cannot dispatch. The same source check applies to `sendRaw` and `findSentByMessageId`; a visible proposal only proves the preapproval step. The earlier populated Gmail/Calendar failures are a separate failure class: [issue #177](https://github.com/waldoco/waldo-backend/issues/177) reports provider/proxy success and missing owner-facing results, while exact turn-specific causes remain unproven.

## What the current Google connection actually grants

[Consent source](../../../packages/runtime/src/connectors/google.ts#L1-L16) and [combined OAuth request](../../../packages/runtime/src/connectors/google.ts#L67-L76) request `openid`, `email`, `calendar.events`, `gmail.readonly`, `gmail.send`, `gmail.compose`, and `tasks` together. The owner-bound proxy stores the refresh token in Supabase Vault; the Worker uses a connection ID and signed operations, not a bearer token ([proxy boundary](../../../packages/runtime/src/connectors/connections.ts#L1-L45), [Edge implementation](../../../supabase/functions/connector-proxy/index.ts#L30-L75)). Scope possession is authorization capacity, not evidence of a working handler or approved effect. These scopes contain no Drive, Docs, Sheets, Slides, or People/Contacts permission. Google classifies `gmail.readonly` and `gmail.compose` as restricted; server access to restricted-scope data can entail verification and a security assessment before general consumer availability ([Google Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), [restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)).

## Smallest safe sequence and acceptance bar

1. **Repair existing paths first.** Derive both proxy method allowlists from a single checked contract or add `tasks`, `sendRaw`, and `findSentByMessageId` in both Worker and Edge proxy with tests that execute each over the signed owner-bound route. Check `get_tasks` open/done/all semantics against Google `showHidden`, `showAssigned`, and `nextPageToken`; either cover these or describe the bounded subset accurately. Keep proxy log lines to method, outcome, typed error, duration, and trace ID. Require owner isolation, rejection of unlisted methods, and red-first regression of the present gap. Stage migration/function/Worker order per the actual diff. Exit: synthetic proxy test proves a successful bounded result and typed 401/403/oversize failure without provider text in traces.
2. **Complete the current owner's narrow loop.** Deploy reviewed privacy-gated diagnostics, rerun the same safe populated Calendar/Gmail and Tasks reads, verify tool result plus Telegram response with turn/trace IDs, inspect Langfuse and Cloudflare for code/outcome only, and capture an actual `proposal_id` plus matching Telegram/console Waiting-on-you card for `send_email`. Test approved sending only to an owner-controlled synthetic mailbox after the proposal and reconciliation rail is verified, with a Gmail `message_id` receipt and one-send outcome; include timeout/duplicate-delivery adversarial tests. Do not call an OAuth grant, proxy `ok=true`, or plausible bot text live acceptance.
3. **Expand read surfaces by owner job.** Start with Drive file search/metadata and selected-file read, then Docs read and Sheets bounded range read. Add each scope only when the user-facing action is ready; keep read output untrusted, bounded, and recoverable by output ID. Use file/resource IDs and ETags/revisions for later writes. Exit per service: second-owner isolation, scope-missing/revoked-grant test, pagination/limit, prompt-injection canary, privacy-safe trace, and one owner-visible live result. Google recommends choosing scopes by the action and least privilege ([scope verification guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)).
4. **Add writes with exact authority.** Prioritize one concrete Docs or Sheets edit only when there is an owner job; require a diff/card containing destination, exact changed range, and post-approval fresh readback with provider revision or updated range receipt. Drive sharing, broad document mutation, Contacts writes, and admin services need separate approval classes and threat review. Full Workspace breadth is a later roadmap, not a release label earned by the current connector.

**Stop/change-direction threshold:** if the signed proxy test still cannot call a declared method, if capture-off synthetic markers appear in any trace sink, if the approval card lacks a persisted ID or owner-bound receipt, or if a provider response cannot be correlated to an owner-facing result, hold that capability at source/configured status and fix that layer before a new OAuth scope or service is added.
