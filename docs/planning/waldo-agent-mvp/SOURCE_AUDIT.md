## Judgment

[inference] Preserve the Cloudflare DO/Supabase substrate and the existing app. The obstacle is not lack of a sophisticated runtime; it is lack of a joined production composition and a complete daily user loop. The alternative hypothesis is that the prototype Supabase agent is faster to extend into the product. Source inspection weakens that option: it is synchronous and separate, its Calendar retry semantics are incomplete, and its chat thread path has an owner-isolation defect. A narrow cloud composition root using existing primitives is the strongest first step; do not force personal chat through the entire work-unit/Kennel machinery.

Falsifier: if an authenticated real-app conversation → one real model call → Calendar read → persisted response cannot be composed through the existing owner boundary without unrelated work-unit machinery, split out a thin personal-agent composition root while retaining the existing owner, scheduler, validation, permission and effect seams. Do not authorize a wholesale rewrite on that basis.

## Twelve findings

1. **The backend production entrypoint is a responsibility API, not a complete personal conversation API.** `backend/packages/runtime/src/index.ts:102-115` returns 404 unless `RESPONSIBILITY_PUBLIC_API_ENABLED` is true and delegates only to the responsibility handler. `backend/packages/runtime/src/responsibility/worker-adapter.ts:135-137` matches responsibility, execution and judgment routes. `index.ts:175-182` already maps authenticated owners into named RunLoop DOs. Retain that identity/owner boundary; add a simple personal turn/read-progress/approval surface. Do not claim that app chat already reaches it.

2. **Live trusted model execution is explicitly closed.** `backend/packages/runtime/src/run-loop/adapters.ts:145-158` constructs a gateway but supplies a `FailClosedSink`, unavailable spend reader and denying safety; it does not supply production ContextComposer or replay-artifact owners. `run-loop/do.ts:1887-1891` unconditionally fails gateway-mode trusted planning before the external call. `adapters.ts:677-680` confirms unconfigured rate-limit admission and no approvals. Production source/context, budget accounting, bounded permission decisions and delivery are engineering work, not environment-variable configuration.

3. **Useful durable substrate already exists.** `backend/packages/runtime/src/run-loop/do.ts:361-371` provisions SQLite schema, scheduler, journal outbox and provider owner. `scheduler/multiplexer.ts:55-100` persists schedules then arms alarms; `:115-147` dispatches with retry/failure/rearm handling. Keep these instead of introducing another scheduler/state owner. However, `run-loop/do.ts:1246-1249` registers only a brief executor; this is not a general shipped reminders/reply-monitoring product.

4. **The current tool list is not implemented action breadth.** Production/default trusted dispatch uses `[getCrsHandler]` at `backend/packages/runtime/src/run-loop/do.ts:2552` and `:2743`. Its `get_crs` handler returns fixed `derived steady`/`steady` values at `:5664-5679`; its effect receipt map is explicitly a local-only fake at `:5698-5704`. Calendar/Gmail/browser adapters must be connected and real health projection must replace this fixture path. Retain schema validation, owner scoping and handler rejection from `tools/dispatcher.ts:141-182`.

5. **Model effect recovery is unresolved separately from real-world action recovery.** `backend/packages/runtime/src/llm/gateway.ts:92-101` issues normal calls but returns `gateway_trusted_receipt_unavailable` on reconciliation. `llm/provider.ts:66-78` expects durable keyed issue/reconcile semantics. Before enabling the gateway, choose a concrete policy: durable captured response where available, otherwise bounded repeat inference with fresh effect identity and accurate cost accounting; never infer that an uncertain message/calendar write was safe to repeat. Avoid making impossible universal exactly-once model inference a prerequisite for the MVP. This is a proposed contract decision, not evidence current code supports it.

6. **The app has useful prototype functionality, but it is a separate backend.** `app/src/agent/agentClient.ts:74-111` invokes Supabase `agent`/`calendar` functions. `app/supabase/functions/agent/chat.ts:85-115` calls OpenAI directly, without a tool loop or streaming. `agent/llm.ts:93-123` makes one structured Calendar/memory proposal; `agent/commit.ts:139-163` performs actual Google HTTP mutations. Reuse app UI, auth, HealthKit and connector learnings, but designate the cloud DO as the sole new personal-agent execution owner. Move the transport and data projection deliberately; do not run both execution engines for the same command. Legacy EF schemas and backend canonical migrations need an explicit mapping, since sharing a Supabase brand does not make their tables/contracts interchangeable.

7. **Legacy chat needs an owner-isolation fix before invited-beta reuse.** `app/supabase/functions/agent/index.ts:22-23,37-50` authenticates a caller but gives a service-role client to chat. `_shared/http.ts:28-34` confirms that client bypasses RLS. `agent/chat.ts:53-70` accepts caller `thread_id` without verifying its owner, then `:78-83` reads history by thread only and `:137-138` updates that thread. `supabase/migrations/0003_chat_and_memory.sql:35-44` has independent user/thread FKs, not an owner-match composite constraint. [inference] A known other-owner thread UUID could expose its history to the model and permit unauthorized thread writes. This is source-backed exploitability reasoning; no exploit or deployed endpoint was tested. Fix/retire this path and add two-owner negative integration coverage, including mismatched IDs. Also `chat.ts:82-83` takes the earliest 20 messages rather than newest 20, so long chats stop supplying recent turns.

8. **Calendar prototype is reusable code, not crash-safe autonomous execution.** `app/supabase/functions/agent/commit.ts:81-105` skips only actions already marked done, then upserts running; a crash after provider success and before durable done can repeat create. `:141-151` calls update without an expected etag and create without a stable provider ID; `_shared/google.ts:109-128` supports `If-Match`, but the caller omits it. `commit.ts:233-240` generates event content without an idempotent provider ID. Build read-before-write/current-version check, bounded self-owned-block grants, stable provider identifiers where supported, read-back and uncertain-outcome reconciliation. Use exact approval for externally meaningful calendar invitations, sends and purchases even if an API offers an undo.

9. **Correctable memory is a product gap despite substantial foundations.** Backend `do-schema.ts:110-166` defines memory blocks/inbox with provenance, validity and conflicts; `recall/gateway.ts:99-109` explicitly describes temporal reads with FTS/ranking/episode search still unavailable. Gateway production context remains unconfigured (finding 2). App migration `0003_chat_and_memory.sql:9-11` defers durable promotion; inspected app chat reads thread history, not memory. Implement a compact explicit preference/fact store plus inspect/correct/forget and commitment tracking before adding graph memory, recursive consolidation or self-improving skills. Corrections supersede facts; facts never generate permissions.

10. **Health is a valuable retained app capability, but freshness/consent must join the cloud loop.** `app/src/modules/health/useHealthData.ts:24-56` has actual HealthKit connection/permission/snapshot calls. `useHealthMetrics.ts:8-15,20-28` computes on app launch and best-effort uploads. `health/sync/syncHealthToday.ts:27-50` gates by sync preference, content watermark and server consent-revoked response; failures retry on later launch (`:52-54`). This supports optional health sharing, not a claim of fresh cloud health while the phone/app never syncs. Build a purpose-limited derived health view with observed-at/freshness/accessibility/consent state; fallback to self-reported energy when absent or stale. Physical-device and cold/offline recovery proof remain required, never inferred from native API calls in source.

11. **Gmail follow-through and proactive delivery are missing endpoints of the loop.** `app/supabase/functions/oauth-google/index.ts:14-16,28-31` grants only Gmail metadata—no body/read/draft/send scope. No Gmail send/history handling was found in inspected runtime/app function source. `app/app/(onboarding)/notifications.tsx:15-21` requests notification permission; searches found no push-token acquisition/registration or provider send pipeline in the inspected app/runtime source. Backend live sink throws at `run-loop/adapters.ts:600-605`. Deliver a token registration/invalidation + owner-bound inbox/Activity + APNs/Expo receipt pipeline, and a bounded approved email-send + response-watch pipeline. OAuth scope/production eligibility work can proceed in parallel; scope approval is not equivalent to an implemented Gmail adapter.

12. **Kennel/browser contracts are seams, not deployed execution; PR release ordering should change.** Outside local environments `backend/packages/runtime/src/run-loop/do.ts:393-395` leaves `workUnitExecutionBridge = null`; local only constructs a binding at `:372-391`. No managed browser executor is bound in the runtime configuration (`packages/runtime/wrangler.jsonc:1-23`). PR plan `docs/planning/WALDO_PERSONAL_AGENT_PRODUCT_ARCHITECTURE_AND_BUILD_PLAN_2026-09-18.md:324-331` puts health after founder alpha, relationships alongside Gmail/health, India corridor before browser and distribution late. `:359-362` makes Trusted Relationships/Drive part of personal-beta sequencing. The user's newer direction warrants a smaller health-aware internal alpha and invited beta without relationships/Drive/Granola/Swiggy/Kennel as gates, plus early read-only managed-browser research and parallel WhatsApp eligibility/Telegram adapter work.

## Proposed engineering order

1. **Composition proof and prototype containment (first critical gate):** pin backend/app contracts, retire or fix legacy chat ownership gap, one user-to-DO binding, app message to real model to persisted response, reconnect and stop. Add one read-only Calendar tool in that proof. Track actual latency/cost. Keep the existing auth and state substrate.
2. **One ongoing personal conversation:** personality prompt/version, compact correctable memory, user priorities/self-report, real app progress/activity and bounded action cards. Persist accepted commands/results and map retry/reconnect behavior. Do not require advanced recall or work-unit planning to chat.
3. **Health-aware daily loop:** optional HealthKit-derived context + timestamps and no-data path; Calendar availability + own focus blocks; exact adjustment proposal or explicit bounded grant; version-checked write and read-back. Physical iPhone acceptance with sharing on/off/revoked and stale context.
4. **Return without another prompt:** durable commitment/reminder schedule, timezone/quiet hours, push registration/delivery, app Activity, snooze/done/cancel. Shut laptop, terminate app, allow cloud wake, reopen and see the same state. This is the first complete health-aware internal alpha, not plain chat as alpha.
5. **Real follow-up:** least-scope Gmail selected conversation context, exact recipient/body/attachment approval, send receipt, uncertain-send handling, response detection and persisted follow-up cancellation. General search/read-only managed browser can run as an independent adapter lane after step 1; browser writes follow the established exact-approval and uncertain-outcome model.
6. **Small invited beta:** memory correction/isolation and duplicate/recovery regressions, measured cost caps, connection revocation, failed-action UX, quiet-hours/proactivity evaluation, real devices/accounts. Basic accurate disclosure and user data controls are necessary product work; do not turn unrelated policy expansion or an agent network into the feature critical path.
7. **Parallel/follow-on:** WhatsApp supported eligibility and channel linking early; Telegram as optional demo/fallback sharing the same owner and history; extend supported browser task families, then Kennel joined proof when a desktop reconnects, then Trusted Relationships/other surfaces as demand warrants.

## Concrete simplifications to PR #138

- Make health part of the smallest complete launch loop, with optional user sharing and self-report fallback.
- Remove Trusted Relationships, selected Drive, Granola, Swiggy and full Kennel from MVP admission criteria; retain their extension seams.
- Consolidate acceptance into three outcomes: adapted day and cloud return; approved follow-up and detected reply; independently bounded later Kennel proof.
- Start browser read-only research earlier but do not build a persistent personal computer/credential vault or browser vendor platform.
- Reuse the existing scheduler/outbox/owner primitives; do not add a second orchestration authority or rebuild the app in native Swift solely for this launch.
- Treat LLM calls, safe reads, idempotent writes, and uncertain irreversible writes differently in recovery. Universal effect machinery should not prevent ordinary conversation from shipping.
- Replace any claim that this is mostly wiring/config with explicit composition, adapter, app migration, physical-device and recovery gates. There is substantial useful source, but no joined production-loop proof was observed in this audit.
