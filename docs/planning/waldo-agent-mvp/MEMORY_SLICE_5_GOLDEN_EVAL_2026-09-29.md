# Memory slice 5 - synthetic development evaluation

This is a measured development fixture, not an independent held-out test. It uses synthetic multi-session owner DO state, with a later city correction, untrusted shared material, and a forgotten trip. There is no live owner data, model answer grading, real provider latency, embedding service or graph expansion. Run with `pnpm --filter @waldo/runtime exec vitest run -c vitest.config.ts test/memory-golden-eval.test.ts`; its `MEMORY_GOLDEN_EVAL` JSON line gives the per-case result, prompt bytes/4 estimate, and aggregate. The fixture was authored with knowledge of the current lexical implementation, so do not call it an unbiased holdout. An independent fixture, kept out of the implementation cycle, plus trial-based answer checks is still needed before selecting another backend.

At source head of this slice, expected claim retrieval is 9/12; expected fact text reaches the *actual turn prompt* in 11/12, since two lexical misses are masked by the small always-visible profile. Forbidden stale/shared/forgotten claim IDs in recall: 0. Unrelated retrieved claims: 2; mean estimated turn-memory prompt cost: 181 tokens. This is not a correctness pass: the Saturday coffee paraphrase does not retrieve the conditional preference and is absent from the profile. A weekend jogging paraphrase misses the long-run claim in recall but happens to see it in profile; an imperial-measurements paraphrase similarly misses lexical recall but sees the metric preference in profile. One other probe retrieves an extra unrelated claim. The test intentionally reports misses rather than weakening the expectation or adding a semantic backend to make it green.

**Forget limitation.** Claim purge now scrubs exact/case-insensitive literal matches in SQL-derived stores and persisted rolling conversation, verifies those stores, and keeps a `purging` retry state on a failed cleanup. It does not identify paraphrases (for example, a different description of a forgotten code word) in any of those stores; `forget-coverage.test.ts` pins this hot-history survivor. The content-free fingerprint blocks exact readmission, not semantic restatement. A model barrier instructs against reusing a forgotten topic but is not a deterministic guarantee. The console must not imply complete semantic erasure. Historical backups and any provider-owned raw conversation retention outside these stores need their own verified retention/purge policy. Until a scoped semantic-safe purge can be verified, do not promise that a forgotten fact can never shape a reply.

**Next decision.** Use a separately maintained synthetic holdout with multi-session query paraphrases, trusted-source changes, corrections, false-match costs, and measured model answers across repeated trials. Compare a cheaper keyword rewrite/expansion or better profile selection against lexical baseline before adding embeddings. A graph backend is not justified by these misses: they are phrase mismatch, not multi-hop relation failures.
