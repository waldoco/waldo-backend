# Event-driven wake migration - design slice, not implementation

September 29, 2026. Owner asked for event-driven design after asking how current patrol works. This document adds a bounded design slice to the heartbeat/cron program. It does not authorize a new send or account access, change current production behavior, or claim a cost saving. Implement after the isolated W/R grader, fixtures, resets and scored trial spine, unless a measured blocker requires it sooner. PR #200 remains an older heartbeat/cron planning artifact; this page describes the migration from the behavior now on `beta-mvp` at `f9b01a4`.

## Current baseline

- Per-owner DO scheduler: a 30-minute deterministic `heartbeat-tick` checks overdue loops and releases held cards; quiet ticks use no model (`packages/runtime/src/channels/heartbeat.ts:7-37,52-125`). Keep scheduled due, quiet-hour release, and missed-run recovery clock-driven. An external event cannot guarantee passage of time.
- A 10-minute `event-brief-sweep` lists events in the next 40 minutes and briefs unseen timed occurrences (`channels/event-briefs.ts:5-19,35-48`). Its executor also checks changed Calendar events and new primary-inbox mail (`channels/telegram-owner-do.ts:1113-1155`; `channels/update-cards.ts:60-67`). It calls the model only for eligible event briefs or change cards. Current `changedEvents` is bounded to `maxResults=50` without next-page traversal, `newMail` takes at most 10, and both cursors are wall-clock milliseconds advanced after calls (`connectors/google.ts:252-261`; `channels/update-cards.ts:60-67`). This can lose changes in bursts or across delayed indexing; address cursor correctness before claiming push parity.
- Scheduled reminders, day cards, nightly consolidation and owner-defined daily standing orders use the existing DO alarm, and Telegram/WhatsApp turn ingress is webhook-driven. Do not replace these with periodic provider fetches.

## Target and bounded slices

1. **Baseline and source registry (no behavior change).** Record, per active owner and connection, polls by provider, provider request count, calls with/without changes, prompt input/output/cache tokens and USD by purpose, p50/p95 notification lag, missed events, concurrent wake count, and alarm lag. Content-free trace only. Count retries separately and preserve no-connection zero-fetch behavior. Compare idle and active owners. Deploy instrumentation in staging first, not a new inference on every tick. Gate: one full-week owner-only baseline, reconciled to provider quota and cost invoices where available.
2. **Calendar source adapter.** For each explicitly connected calendar, register a renewable provider push watch only if account scopes, channel verification and lifecycle are viable; notifications are hints, not content or authority. Authenticate provider delivery, bind opaque channel/resource identifiers to owner, reject unknown/wrong/revoked channels, persist high-water mark and queue one owner-scoped reconcile. On event, fetch changes via a provider-native sync token with full pagination and deleted items; atomically commit cursor with admitted changes after processing. If token expires or a watch gaps, perform bounded full reconciliation before rearming. Renew before expiration; on disconnect/deletion remove watch and cursor. A watch must not broaden calendar scope. Material change can recalculate an occurrence-based pre-event alarm (`start - lead`), but preserve a fallback clock sweep/reconciliation for changes while watch is down. Avoid duplicate brief when start changes; key on event identity plus occurrence/start and assess whether a moved event deserves a new brief.
3. **Gmail selected-watch adapter, separately permission-gated.** Do not infer mailbox-wide monitoring from OAuth read scope. Start only for an explicitly authorized account/thread/search scope and after the production restricted-scope gate. `users.watch` + Pub/Sub notification must authenticate project/topic and webhook, then use `history.list` from a persisted history cursor with pagination; notification IDs are hints and may be duplicated/out of order. Recover expired history, renew watch, filter self-sends and unrelated messages, and stop watches on revoke/deletion. An empty/disabled watch does not poll mail. Existing `IMPLEMENTATION_CONTRACTS.md:166` is the permission/security floor, not proof this exists today. Until this passes, keep bounded selected-thread polling for authorized follow-through, not universal ten-minute mailbox fetch.
4. **Batch and gate.** Coalesce provider events per owner/source into a short bounded debounce; apply high-water/dedupe to source identifiers and event versions. Separate a cheap deterministic change admission layer (auth, relevance, time/quiet window, already-sent occurrence, user volume) from an optional model summarization step only when the batch has useful changes. Keep immutable source references, owner/source taint and a complete audit of skipped, held, sent and failed. Do not silently widen content read, push audience or AI context. Use one owner-DO serial reconcile or a bounded queue when bursts exceed it; don't block a user turn behind a long provider scan.
5. **Idle timeout and fallback.** Split clocks: exact/meaningful alarms for due reminders, pre-event brief windows, quiet-hours release, nightly and active standing orders; low-frequency, jittered source health/reconcile for watchers and lost-notification recovery; no fixed high-frequency fetch for an idle owner with a healthy watch. A monitor with a real deadline keeps its own deadline alarm. Use bounded stale thresholds and an explicit fallback interval only while watch is unhealthy; do not silently increase polling. If a provider offers no reliable push, keep a justified adaptive poll for that source with observed latency/cost bounds. Watch liveness must be external to a potentially dark owner DO; DO heartbeat alone cannot prove a nightly run or a lost provider push.

## Invariants and failure tests

- Notifications cannot cause effects by themselves: owner authorization and current send/effect gates are checked at execution. Authenticated ingress is not permission; never treat event bodies as instructions. Prevent cross-owner binding, spoofed webhook, duplicate notification, stale/reordered cursor, self-event echo, renewal race, revoked account, quota backoff, calendar cancellation/reschedule, missed pre-event window, quiet-hours boundary, and burst pagination loss.
- Stage replay tests with duplicate/out-of-order notification, full pagination (>50 events, >10 messages), expired sync/history cursors, provider outage and reconnect, schedule alarm crash/retry, DO eviction, owner disconnect and account deletion. Compare exact final user-visible cards and source readbacks against the present polling baseline. No production cut without owner review and rollback to bounded polling; never claim zero missed events solely because the provider watch was registered.

## Cost model and exit

Let `U` be connected owners, `P` current polls/owner/day (Calendar and mail from a shared 10-minute sweep: up to 144 checks/source/day, plus event lookahead), `E` admitted source event batches/owner/day, `R` watch renewals/owner/day, `F` fallback reconciliations/owner/day, and `M` model-eligible batches/owner/day. Current read volume is roughly `U * P` per source, plus per-result detail reads; target is `U * (E + R + F)` provider requests, with pagination and retries counted. Model spend is not `P * token_cost` today because quiet sweeps skip the model; compare `M * actual_tokens_by_purpose * model_price`, not poll savings masquerading as token savings. Add watch/PubSub/queue/DO alarm charges, idle reconnect and provider quota. Measure light/typical/heavy distributions and p50/p95 event-to-notification latency at 20, 1,000 and 10,000 simulated owners; set thresholds from observed baseline and user experience before commit. Exit only with a measured cost delta, no regression in missed/late notifications or owner isolation, and an audited rollback.
