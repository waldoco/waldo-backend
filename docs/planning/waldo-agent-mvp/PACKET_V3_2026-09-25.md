# RCA: why v3 failed at step 1 (2026-09-25)

## What happened
`supabase db push` applied all three pending migrations to the REMOTE project
(exit 0, correct). `supabase test db` then ran against the Mac's long-lived
LOCAL Supabase database (exit 1, 8 failures across 4 files). Every failure maps
to stale local schema or dirty local data - none to the repo:

- `console_session_open` does not exist -> migration 20260925010000 never applied locally
- presences/link_codes reject provider 'whatsapp' -> 20260925110000 never applied locally
- grant-contract tests 10/14 unexpected EXECUTE grants -> grant-tightening migrations missing locally
- invite count have-2-want-1 and a non-null stale attribution -> leftover rows from a previous local run

## Root cause
`supabase test db` runs pgTAP against whatever the local database currently
holds. It does not apply pending migrations and does not clear data (Supabase
CLI reference: db reset is the command that recreates the local database and
re-applies migrations + seed). CI never hits this because verify.yml starts the
local database from zero (`supabase db start` on a fresh container) before
`test db`. The Mac's local stack persists for days, so it silently drifts
behind the repo - in schema and in data.

## Why it keeps happening
Second occurrence of the same class (first: the migration-fixture drift fixed
by guard-migration-fixture-sync.mjs). Mac-side machine state is invisible to
repo-side gates; the repo cannot test the laptop. The durable fix is therefore
procedural, and it is now pinned in the checklist (Database tests): any runbook
or CI step that runs pgTAP first rebuilds local state, so the tests prove the
repo, not the machine.

## Was Codex doing something wrong?
No. The stop was correct, the evidence capture was complete, and its two
judgment calls were both right: ddc15ff-vs-dd6ed9e was docs-only, and its
inference (local DB missing this week's migrations + stale data) matches this
RCA exactly. One clarification so nobody "fixes" it: `supabase/config.toml`
`project_id` is the LOCAL stack name, not the remote project ref - it is
supposed to differ from the linked project togdshayyxycitzckpqv.

## Remote risk
None. The three migrations reported applied to togdshayyxycitzckpqv, and the
failing assertions target objects those very migrations create or alter, so the
failures are local-only by construction. `supabase db push` in v3.1 verifies
"up to date"; `supabase test db --linked` is available if direct proof against
the remote is wanted.
