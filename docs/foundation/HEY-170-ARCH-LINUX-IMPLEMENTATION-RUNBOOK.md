owned by HEY-170. This runbook is for Ashish's Arch Linux installation and its local containerized
Supabase stack.

grants and default privileges`.


- a JWT, personal access token, or private key.

The `project_id` in `supabase/config.toml` is only a local Docker namespace. It is not permission to
link a hosted project.

Additional hard boundaries:

- Add one forward migration. Never edit any of the seven files already merged by HEY-134.
- Do not create a `SECURITY DEFINER` function.
- Do not add runtime, Worker, Durable Object, app, provider, delivery, or service-role fallback code.
- Do not weaken, delete, skip, or mark an existing pgTAP/RLS assertion expected-to-fail.
- Do not use real user or health data. Use only the existing synthetic fixtures.
- If a clean local cycle requires `db reset --local`, that is allowed. Never reset a hosted project.

Stop immediately if a command attempts to authenticate, asks for a hosted project password, shows
a linked project, or lacks `--local` where the command can target a hosted database.

## 2. Required result

The completed PR must prove this exact contract:

| Function | Direct caller contract |
| --- | --- |
| `public.app_user_id()` | `authenticated` only |
| `public.enforce_consent_audit_history()` | trigger-internal only |
| `public.health_daily_requires_consent()` | trigger-internal only |

For all three functions, `PUBLIC`, `anon`, and `service_role` must have no direct `EXECUTE`.
`authenticated` must also have no direct `EXECUTE` on the two trigger-only functions.

Future functions created in `public` by the observed object-creating role must not automatically
grant direct execution to `PUBLIC`, `anon`, `authenticated`, or `service_role`.

Revoking direct execution must not break the existing triggers. A write performed as
`service_role` must still invoke the consent triggers and enforce their constraints.

- **Adapter:** a forward migration generated by pinned Supabase CLI `2.109.1`.
- **Impact Surface:** one new migration, pgTAP tests, exact migration-history/static guards, and

## 9. Inspect the live local database before migration SQL

Create the following diagnostic query outside the repository:

```bash
cat > "$EVIDENCE/inspect-function-security.sql" <<'SQL'
with targets(signature) as (
  values
    ('public.app_user_id()'),
    ('public.enforce_consent_audit_history()'),
    ('public.health_daily_requires_consent()')
)
select
  p.oid,
  format('%I.%I(%s)', n.nspname, p.proname,
         pg_get_function_identity_arguments(p.oid)) as regprocedure_signature,
  pg_get_userbyid(p.proowner) as owner,
  p.prosecdef as security_definer,
  p.proacl
from targets t
join pg_proc p on p.oid = to_regprocedure(t.signature)
join pg_namespace n on n.oid = p.pronamespace
order by regprocedure_signature;

with targets(signature) as (
  values
    ('public.app_user_id()'),
    ('public.enforce_consent_audit_history()'),
    ('public.health_daily_requires_consent()')
)
select
  p.oid::regprocedure::text as regprocedure_signature,
  coalesce(grantee.rolname, 'PUBLIC') as grantee,
  privilege_type,
  is_grantable
from targets t
join pg_proc p on p.oid = to_regprocedure(t.signature)
cross join lateral aclexplode(coalesce(p.proacl, acldefault('f', p.proowner))) acl
left join pg_roles grantee on grantee.oid = acl.grantee
order by regprocedure_signature, grantee, privilege_type;

select
  tg.tgname as trigger_name,
  tg.tgrelid::regclass::text as relation_name,
  tg.tgfoid::regprocedure::text as function_signature,
  tg.tgenabled
from pg_trigger tg
where not tg.tgisinternal
  and tg.tgfoid in (
    to_regprocedure('public.enforce_consent_audit_history()'),
    to_regprocedure('public.health_daily_requires_consent()')
  )
order by trigger_name;

select
  d.defaclrole::regrole::text as object_creating_role,
  coalesce(n.nspname, '<all schemas>') as schema_name,
  d.defaclobjtype,
  coalesce(grantee.rolname, 'PUBLIC') as grantee,
  acl.privilege_type,
  acl.is_grantable
from pg_default_acl d
left join pg_namespace n on n.oid = d.defaclnamespace
cross join lateral aclexplode(d.defaclacl) acl
left join pg_roles grantee on grantee.oid = acl.grantee
where d.defaclobjtype = 'f'
  and (n.nspname = 'public' or d.defaclnamespace = 0)
order by object_creating_role, schema_name, grantee, privilege_type;
SQL
```

Execute it only against the local database:

```bash
"${SUPABASE[@]}" db query --local \
  --file "$EVIDENCE/inspect-function-security.sql" \
  2>&1 | tee "$EVIDENCE/inspect-function-security.log"
```

Review and record:

1. Exactly three non-null zero-argument function identities and their OIDs.
2. The owner of each function.
3. `security_definer` is false for all three.
4. Every current direct `EXECUTE` grantee, including implicit `PUBLIC` privileges.
5. `enforce_consent_audit_history` is attached to `public.user_consents`.
6. `health_daily_requires_consent` is attached to `public.health_daily`.
7. The actual role that owns the applicable future-function default privileges.

Do not assume the role is `postgres`. The migration may name it only after the query observes it.
If owners differ, a signature is missing/overloaded unexpectedly, or no applicable default owner can
be established, stop and report the output before writing migration SQL.
