# One work list (W3, R1): design

Status: proposal, 18 Nov 2026. Owner ruled R1 in ("Yes, all of it", waldoco/waldo-app#257, 6979482103). Builder: Ark. App side: Suyash (app#294).

## The decision

`loops` becomes the one list of work Waldo carries. Every item records what done looks like, where it came from, what Waldo told the owner and when, the owner's last word, and its status. Owner chat and the app read and close the same rows. The other stores keep their clocks and their contracts, and point at a loop row; they stop being separate lists.

Done when (18 Nov plan):

- the eval where a correction closes its item passes;
- no nudge goes out twice in a day;
- no item is raised again after the owner said it was done.

## Design

### 1. The row

Additive columns on `loops`, added with the `pragma_table_info` check the books already use (`quests.ts:60-61`):

| Column | Meaning |
| --- | --- |
| `kind` | `promise` (Waldo said it would), `follow_up` (Waldo watching something), `mail`, `owner_task` (the owner's own to-do), `reminder`, `quest` |
| `done_when` | One line in the model's words: what makes this done. Required on new rows; old rows read NULL. |
| `source_kind`, `source_ref` | The pointer: a mail `source_ref`, a reminder id, a quest id, a chat turn id. Mail keeps `loop_mail_sources` for its nudge state. |
| `owner_word`, `owner_word_at` | The owner's last word on this item, short, in their own words. |

`origin` (owner, waldo, mail) comes from #2165. Status stays `open`, `done` or `dropped`. `waiting` (blocked on someone else) is a candidate if the evals show the model needs it.

### 2. What Waldo told, kept

A table `loop_told(loop_id, told_at, record_id, surface, text, delivery)` is written by `settleFinal` when a delivered record names loops (`heartbeat.loops`, `mailFollowup.loopId`, and new loop ids on day cards and update cards). It holds:

- the sent text, at most 500 characters, under the same rules as chat history (it is a message the owner already has);
- the delivery state.

This is the one place to answer "did Waldo already raise this today?". The rule "no nudge twice in a day" becomes a read of `loop_told`, not a cooldown spread across three stores. The table is bounded: 20 rows per loop and 90 days.

**Open for the owner:** keeping the sent text in the owner object. It is chat text the owner holds already, and conversation bodies are normal context within the owner's authorization (CLAUDE.md). Health words in a sent message follow the beta ruling for owner-channel replies: kept, never logged. Without the text, `loop_told` keeps ids and times only, and the model can't see how it worded the last nudge.

### 3. The owner's word, and closing from chat

- The owner turn sees one "Work Waldo is carrying" section: open items, each with its last told time and the owner's word. It replaces `loopsSection` and `openLoopsPrompt`.
- `close_loop` gains an optional `owner_word`. A new `note_loop {id, owner_word}` records what the owner said without closing the item.
- Which item a sentence refers to, and whether it closes it, is the model's judgment, with scenario evals (W9). No keyword rule decides it.
- Mail items become closable from chat through #2185's change, which W3 keeps and widens to every kind.
- The app reads and closes the same rows through #2178's routes. `watching` lists `follow_up` and `promise` items today. W3 widens `source` additively and adds `kind`, which needs a new contract version, not a widened v1.

### 4. Folding the other stores

| Phase | Store | How it folds | Owner of the code |
| --- | --- | --- | --- |
| 1 | `loops`, mail, Waldo's own follow-ups | Columns, `loop_told`, the turn section, `note_loop`. Behind `WORK_LIST=1` (staging 1, production 0). | Ark |
| 2 | Reminders | `set_reminder` also writes a loop row (kind `reminder`, pointer = reminder id). The schedule stays the clock. Firing writes `loop_told`; a one-shot closes its row as done when delivered. | Ark |
| 3 | Quests | A quest gets a loop row (kind `quest`, pointer = quest id). The `goals` table and ADR-0064 stay the record; check-ins write `loop_told`. | Ark, with Ansh for ADR-0064 |
| 3 | Goal claims | No fold. A goal claim stays memory. If a goal carries a commitment, the model opens a loop pointing at the claim id. | Ansh (W5) |
| — | Responsibilities | Delete the dead module and its tool names. Removing names from `packages/contracts` is a removed contract field, so it needs the owner's ruling (as HE-10 does). | Ark, after ruling |

### 5. What changes in the evals (W9)

Three cases from the 17–18 Nov transcript, graded on outcome, run before phase 1 merges and failing on today's code:

1. The owner says an item is done; it closes and is not raised again that week.
2. Two runs on the same day each find the same open item; only one tells the owner.
3. A mail item and a calendar event about the same thing appear once, as one item with two sources.

## Sequencing and seams

- Phase 1 starts after #2185 merges: it owns `loops.ts` and `scheduled-run.ts` lines today. #2165 and #2178 merge before or with phase 1.
- `owner-do.ts` gets one wiring hunk per phase; `owner-turn.ts` gets the section.
- Every change is behind `WORK_LIST`. Rollback is `WORK_LIST=0`. The added columns and table stay, unread.
- No Supabase migration. Owner-object schema only, additive.
