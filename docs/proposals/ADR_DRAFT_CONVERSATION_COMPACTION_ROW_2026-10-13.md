# ADR draft: a compaction row for long conversations (model view only)

Status: approved by the owner on 13 Oct (about 20:31Z, "go with the 1182 compaction plan"), amended after the independent reviews of `010e4b2c` and `0e4b42a8` without leaving what was approved. The core is built behind its switch (`conversation/compaction.ts`); the post-delivery call and the flip follow. It becomes an ADR in Brain under the next free number, and the B2 build carries that publication.

Author: the backend lead session (claude.ai/code `session_01ARsyYdWNBCNEUBLNrnbtrP`). Source read at `beta-mvp` `aae96328`, re-read at `9440ec6a` for the amendment.

## 1. Context

**The window drops rows silently.** The owner turn bounds the model's conversation input with a token-aware rolling window: `packages/runtime/src/conversation/window.ts` keeps the newest rows that fit `CONVERSATION_INPUT_BUDGET_TOKENS` (about 100k tokens, the wire ceiling tightened to the model's usable window), oldest rows dropped first, the current owner turn always kept, "overflow degrades to a shorter window, never to a failed turn" (`windowModelMessages`, lines 41–61). `conversation/joined-path.ts:66–70` applies it to the ancestor path before every model call and reports `kept`, `dropped` and the token estimate to the `context_window` trace hop (`channels/owner-turn.ts:254`). Nothing replaces what is dropped: no summary, no marker in the model's view, no note to the owner. A fact the owner stated early in a long thread leaves the turn's context the moment the window passes it, unless the claims store or episode recall happens to carry it.

**What this costs the owner.** The owner named "loses context" as the first of three pains (14:38Z ruling). The window is exactly where a long conversation loses it, and the loss is invisible: the reply simply stops knowing.

**What exists already.** Durable facts go to the claims store (`memory/claims.ts`) through the `remember` path and the nightly pass; episode recall (`search_episodes`) retrieves past rows just in time; the tool-output ledger keeps the newest six tool fragments per kind across turns. None of these is a summary of the conversation's own thread: who asked what, what was decided, what is still open. The contracts package has a working-memory carry-over shape (`contracts/src/runtime/working-memory.ts`: bounded buckets of `summary` + `source_ref` + `source_taint` entries) with no runtime reference today.

**Reference systems.** Anthropic's context-engineering guidance: "Compaction is the practice of taking a conversation nearing the context window limit" and "Structured note-taking, or agentic memory, is a technique where the agent regularly writes notes" (anthropic.com/engineering/effective-context-engineering-for-ai-agents). Claude Code: "Compaction replaces the conversation with a structured summary. System prompt, CLAUDE.md, memory, and MCP tools reload automatically", and the summary keeps "your requests and intent, key technical concepts, ... pending tasks, and current work" (code.claude.com/docs/en/context-window). Letta's `memory_rethink` rewrites a block wholesale; Mem0 and Graphiti keep facts, not threads. The pattern Waldo needs is the Claude Code one applied to the dropped span only: the recent rows stay verbatim, the dropped span becomes one summary.

## 2. Decision

**A compaction row.** When a conversation grows past what the model's window can carry, the runtime writes one **compaction row** that summarises the oldest part of the chain, and the model's view becomes `[compaction row] + [a verbatim tail]`. The transcript the owner sees keeps every row unchanged; the compaction row exists in the model's view only.

### 2.1 Shape

- A conversation entry with the entry role `compaction` (`ConversationEntry.role?: ConversationRole | 'compaction'`; `ConversationModelMessage.role` stays `'user' | 'assistant'`, so no provider adapter can receive a compaction role on the wire), `modelPayload` = the summary text, `appPayload` = `''`, an own optional field `covers: { from_id, to_id, rows }` naming the first and last row ids it summarises and how many rows that is, and the ordinary `modelProjection` (`include`, `omit` or `replace`; no new projection mode, so `covers` survives a projection change). Stored by the **canonical owner conversation store**, the one durable writer of the chain (`conversation/canonical-owner-store.ts`); no new table, no new store. The row is appended as a child of `covers.to_id` with that row's `threadAnchorId`, a side branch beside the first kept row, so no stored row changes.
- **What it covers.** Everything older than a verbatim tail of whole rounds whose estimated tokens are at or under `COMPACTION_TAIL_FRACTION` (50%) of the input budget; the cut falls on a round boundary, so the tail starts with an owner message, and the newest round always stays in the tail whatever its size, as the window always keeps the current turn. The compaction call's input is bounded to the model's input budget: the live summary first, then the newest rows of the span that fit; rows older than those stay dropped exactly as today, counted in the `compaction` hop as the gap, so a chain that already exists when the switch turns on compacts rather than failing as oversized. `covers.from_id` is always the first original row whose content the summary carries, directly or through the previous summary, and `covers.rows` counts original rows; the previous compaction row is an input to the call, never the span's start. A later compaction therefore supersedes the earlier row in one write with the new row: the superseded row keeps its id and `covers` for audit, its summary text becomes a fixed marker and its projection `omit`. "Live" means a compaction row whose projection is not `omit` and whose `to_id` is on the leaf's ancestor path; the view rule and the idempotency key both read that definition. No superseded summary is retained: derived personal data, possibly with qualitative health, lives only in the one live compaction row of a chain, and the chain's own rows keep their retention under the health plane amendment.
- **Rendering.** The model sees the row as one `user` message that opens with `[Waldo's summary of N earlier messages in this conversation; not the owner's words:]` and closes with `[End of summary.]`, so nothing grounds on it as the owner's statement. `appContext`, `appTranscriptPage` (which keeps only `user` and `assistant` rows, `channels/app-api.ts:197`) and the Telegram and iMessage transcripts never carry it; `speakerOfEntry` maps it to `system` and the episode wrapper skips it, so it never enters the index or the nightly pass. No app.v1 change.
- The summary is bounded at 2,000 output tokens, written in the owner's language, as plain bullets (never numbered steps, which the numeric floor in 2.3 would reject), structured as: what the owner asked for and decided, with the owner's latest correction superseding earlier statements; open items and promises Waldo made; facts the owner stated that are not yet in memory, each marked as stated by the owner; nothing about tool mechanics. A truncated output is a failed attempt, not a summary.
- Conversation rows and summaries carry no taint field; they are null-taint by construction, which is why the health check in 2.3 is explicit.

### 2.2 The view, the trigger, and who writes

- **The view always keeps the compaction row.** `compactedHistory` finds the chain's live compaction row whose `covers.to_id` is an ancestor of the leaf, windows the rows after `to_id` against `budget - tokens(C)` with today's drop-oldest rule, and prepends C. The window's estimator and fallback are unchanged for the rows after C; C itself is exempt from the drop. The earlier draft's "the window is unchanged and C is simply the first row it sees" was wrong: `windowModelMessages` drops index 0 first, so C would have been the first row lost.
- **Trigger, per chain, after delivery.** The reply is delivered first; the compaction then runs in the background under the owner's run scope (`scope.admit()` before the call and before the write), never inside the turn and never through the turn's error path, so a compacting turn is no slower and a compaction error cannot fail a turn. It runs when the turn's window reported `dropped > 0` or `estimated_tokens` above `COMPACTION_TRIGGER_FRACTION` (70%) of the budget, the chain holds at least `COMPACTION_MIN_OWNER_ROWS` (10) owner rows with `createdAt` later than the live compaction row's `createdAt`, and the chain's last compaction attempt, success or failure, is older than `COMPACTION_MIN_INTERVAL_MS` (one hour). The attempt time is one bounded per-chain value with no content. With the trigger at 70% and the tail at 50%, the two limits are backstops; a failing compaction (a rejected summary, an oversized input, a truncated output, a model error) therefore retries at most hourly.
- **Writer and I/O order:** the compaction is a model call (external I/O) and therefore runs outside the owning SQLite transaction; one compaction per chain at a time, idempotent by `(chain, to_id)`; the row and its witness are appended in their own transaction without touching the chain's leaf key (an append, or a compare-and-set on the leaf), so a turn that lands while the summary is in flight is never forked off a stale leaf. If anything fails, nothing is written and the view is exactly today's.
- **Judgment:** what to keep in the summary is the model's call under the instruction above; no regex or rule decides what mattered.

### 2.3 Privacy, authority and forget

- **Destination:** the summary is produced through the Scribe with destination `internal_context`, the same destination class as the rows it summarises. Owner health text follows the beta ruling for conversation rows (it may reach model context and owner-channel replies; never logs, audit records, R2 summaries, browser jobs, third-party sends or bulk long-term memory). The compaction row is conversation context, not long-term memory: it is not a claim, it is not promoted by the nightly pass, and it carries no `verification_status`.
- **Numeric health, enforced before the write.** The Scribe's free-text health scan is off for null-taint text at `internal_context` (`scribe/sanitiser.ts`, the owner's decision of 28 Sep), so the instruction alone would be the only guard. Before a compaction row is written, the summary text passes the Scribe's exported **numeric-only** predicate (`numericHealthIn`), built on its non-global matcher over the patterns it owns or imports: `RAW_SENSOR_PATTERNS` and `DERIVED_SCORE_PATTERNS` from the contracts, which are shared `gi` regexes and stateful under a bare `.test()`, plus the numeric half of `HEALTH_FREE_TEXT`, which is declared apart from its qualitative half so a later qualitative entry cannot join the floor by accident. On a match nothing is written and the attempt counts toward the hourly backoff. The full free-text scan is not reused, because its qualitative entry would reject lines policy (a) keeps ("circadian rhythm is off"). This is the existing Art-9 floor applied at a new write, not a new judgment rule; it also rejects an ordinary numbered list ("Next steps: 1."), which is why the instruction asks for plain bullets and the flip PR reports the reject rate. Falsifiers: "slept 5 hours" is rejected, twice in a row; "sleeping badly this week" is written.
- **Authority:** a compaction row never grants or records authority. Approvals, receipts, effects and open-loop closure read the ledgers, never the summary; the summary may say "the owner approved X", and the desk still decides from its own rows.
- **Forget:** `redactConversationEntries` reaches the summary text by literal needle like any row. In addition, a forget whose topic sits in any original row inside a compaction's `covers` span, or in the summary itself, sets that row's projection to `omit`, replaces its summary text with the fixed marker and keeps `covers`, rewriting the row and its witness in one unit (the hit test reads the rows as stored before the literal rewrite). Because `covers` names original rows, a summary of summaries that carries the topic forward is reached the same way. The next compaction is rebuilt from the redacted rows, so a paraphrase of the forgotten topic is neither kept nor reintroduced. Forget and the store's shape check always run, whatever the switch says. A forget barrier applies to the summary as to any stored text.
- **Logs and traces:** the `context_window` hop gains a `compacted` count beside `kept` and `dropped`, and a `compaction` hop records ms, rows covered, output characters and the gap. The `compaction` purpose is `metadataOnly` in the model-call logger, which strips the text from the failure line and the success line alike, so the summary never reaches a trace.

### 2.4 What stays as it is

- The window's budget, estimator and drop-oldest rule (`window.ts`) are unchanged for the rows after the compaction row.
- The claims store, episode recall and the tool-output ledger are unchanged; the summary does not write memory and is not indexed.
- Threads (the app's per-thread chains) get the same mechanism per chain; one live compaction row per chain.

## 3. Alternatives considered

1. **Raise the window.** The 100k cap is the cost rule (cheapest-passing routing); doubling it doubles the cost of every long turn and still drops silently past the new line. Rejected.
2. **Retrieval only (episodes).** `search_episodes` already brings back rows the model asks for, but the model cannot ask for what it does not know it lost; retrieval is a complement, not a replacement. Rejected as the sole fix.
3. **Whole-conversation compaction (Claude Code's default).** Replaces everything with one summary; the recent rows the owner is mid-conversation about should stay verbatim. Rejected in favour of summarising the dropped span only.
4. **Per-turn structured notes written to memory.** The claims store already does this for durable facts through `remember` and the nightly pass; conversational continuity ("we were in the middle of planning Thursday") is not a fact to remember forever. Rejected for this problem; the two compose.
5. **Working-memory buckets (the unused contract).** Fixed buckets with caps fit a coding agent's work log; a personal conversation needs prose continuity. The contract can stay for the browser/work paths; not used here.

## 4. Consequences

- **Benefits:** a long thread keeps its decisions and open items in the model's view; the loss becomes legible (the summary says what it covers); cost is bounded (one extra model call per compaction, at most one attempt per chain per hour, output at most 2k tokens, on the cheapest model that passes the section 6 eval).
- **Costs and risks:** one more entry role and one more place the forget must cover (both tested); a summary can be wrong, which the verbatim tail limits and the owner can correct ("that's not what I said" lands as a normal turn, and the next compaction supersedes it with corrections instructed to win); the model view changes shape, so the L1 scenario harness needs a case for it.
- **Impact surface:** `packages/contracts/src/runtime/conversation-entry.ts` (a persisted-record contract: the entry role, `covers`, the rendering), new `conversation/compaction.ts`, `conversation/canonical-owner-store.ts` (the shape check and the append), `conversation/joined-path.ts` (the view), `channels/owner-turn.ts` (the post-delivery trigger and the hops), `channels/conversation-store.ts` (forget), `channels/episodes.ts` (the skip), the Scribe's exported numeric patterns; tests for each; no app.v1 change; no Supabase, wrangler or migration change.
- **Switch:** `COMPACTION.enabled = false` in `conversation/compaction.ts`, off until the section 6 eval meets its bar. It gates the trigger and the view rule only: off means the plain window, exactly as today, with any rows already written stored and inert; forget and the store's shape check run regardless. Rollback is the switch flipped back and deployed.
- **Process:** this record is not authoritative until it is published in Brain under the next free number and `docs/foundation/accepted-adrs.json` is regenerated; the B2 build carries that publication.

## 5. Decisions the owner made (13 Oct, about 20:31Z)

1. The compaction row is a conversation-store row kind written by the canonical store (the writer stays the same; the row kind is new).
2. Health policy (a): qualitative owner health may appear; numbers are instructed out and Scribe-checked. Policy (b), no health text at all, stays available as one line in the instruction and one assertion in the test, on the owner's word.
3. The budget: the trigger at 70%, output at most 2,000 tokens, at most one compaction per ten turns and per hour; the switch stays off until the eval shows the recall gain.
4. The owner does not see the summary yet; it is a later app surface, contract first.

Set by the lead within that approval after the 23:17Z and 00:10Z reviews: the numeric-only check as the Scribe check of decision 2; the 50% tail; the attempt-based hourly limit; ten owner rows counted by `createdAt`; the input bound and the gap; the atomic supersede; the section 6 eval bar.

## 6. Tests and falsifiers (for the build)

- The view: the compaction row is in the model input whenever the chain has one, whatever the window budget; the tail is whole rounds at or under 50% and starts with an owner message.
- A 60-turn conversation where turn 3 states a preference and turn 60 asks about it: with the switch off the model's view lacks turn 3 and the reply cannot know it; with it on the compaction row carries it and the reply does (L1 scenario with model-input assertions on both).
- The eval bar for the switch, with a real model and a scripted long conversation, run with the switch on and off. Two safety probes must pass outright, and any failure blocks the flip: a forgotten topic never resurfaces, and no approval is invented. Five recall probes are scored: a correction from the compacted span where the owner's latest version wins, a name, a commitment, a decision, and one fact that survives three successive compactions. The switch turns on when the switch-on run answers at least four of the five and the switch-off run answers fewer; the flip PR carries both counts and the numeric-floor reject rate.
- The app transcript page never contains a compaction row; the Telegram and iMessage transcripts neither; the episode index has no row for it.
- Forget: a topic stated inside the span sets the row to `omit` with the marker, keeps `covers`, keeps the witness valid, and the next compaction does not reintroduce it; a topic stated before the first compaction and forgotten after a second exists sends the second to `omit` as well.
- A chain longer than the compaction input budget compacts, and `covers.from_id` is the oldest row that fitted.
- Health: a fake summary "slept 5 hours" writes no row and counts as an attempt; "sleeping badly this week" is written.
- Hostile: a compacted assistant row that quotes injected instructions; the desk and the effect ledger are unchanged.
- Concurrent: two turns on one chain end together; one compaction runs and the stored leaf is unchanged.
- The desk's decisions are identical with and without a compaction row that mentions an approval.
- A failed, truncated or rejected compaction leaves the chain and the next turn exactly as today, and the next attempt waits an hour.
- Cost: a 100-turn scripted run inside one fake hour makes at most one compaction; across fake hours, at most one per ten owner rows.
