# Memory v2: a personal assistant's notebook over one store of facts (25 October 2026)

Status: **proposed, for gate review before code.** This widens #1534 (the owner profile) to the whole memory model. The welcome
constellation ([`WELCOME_CONSTELLATION_2026-10-25.md`](WELCOME_CONSTELLATION_2026-10-25.md)) is v2's first producer. It stays
separable, so it can ship in the cohort deploy on its own. ADR draft: [`ADR_DRAFT_MEMORY_V2_2026-10-25.md`](ADR_DRAFT_MEMORY_V2_2026-10-25.md).
Base: `beta-mvp` `2c4672c9`.

## The owner's direction

Think like a human personal assistant on day 1: learn about the person, write it down, understand it, and keep it current.
SQLite stays the main store. Adopt the markdown-notebook pattern that current personal agents use. Every line keeps its source.
A forget deletes everywhere. Raw health numbers are never persisted in DO memory or in markdown.

## The decision in one paragraph

**Claims stay the one truth. Every markdown page is derived from them, or from episodes, and every line cites its source.**

Waldo keeps a store of atomic, sourced, forgettable facts (claims). On top of it, one writer compiles two markdown notebooks:
- **About you**, a USER.md-style page, read on every turn, bounded;
- **Journal**, one page per day of what happened and what Waldo did, searched and not injected.

The constellation is the visual of long-term memory over the same claims. The owner edits *About you* line by line. Each edit
lands on the claims that line cites, and the page recompiles. So no markdown page is ever a second truth.

This is the lesson of 24 Sep. Commit `5ddd685d` replaced Waldo's four markdown core files (MEMORY_CORE, MEMORY_GOALS,
MEMORY_FOLLOWUPS, intelligence-summary) with claims. Whole-file model edits had no per-line provenance, and a forget could not
prove where a fact had gone. v2 brings back the readable notebook without the flaw.

## The four layers

### 1. Short-term: the conversation window

This is unchanged. Compaction stays off for the cohort (#1458 and #1546 carry its fence). When compaction turns on, its summary is
derived memory under the forget barrier (ADR-0085 rule 3). It is never a notebook writer. Before compacting, a flush step runs,
as OpenClaw's does. It hands the window about to be summarised to the claim writer (the same claim ops the nightly pass uses),
so nothing learned in a long chat is lost to the summary.

### 2. Episodic: episodes plus a daily journal

- **`episodes`** (existing): FTS5 over raw messages, read by turn recall and `search_episodes`.
- **`journal_days`** (new): `(day TEXT PRIMARY KEY, body_md TEXT, refs_json TEXT, written_at, version)`. One markdown page per
  local day, sections fixed: *What happened*, *What Waldo did*, *Open threads*. Each line ends with its refs (episode entry ids,
  run ids, card ids, claim ids) in a trailing `⟨e:…, r:…, c:…⟩` marker that the app renders as a source chip.
  - **Writer:** the nightly job only, after its claim ops. The day's episodes, runs, cards and approvals go in; the page comes
    out through a structured call (`{ lines: [{ section, text, refs[] }] }`). Code checks that every ref exists and belongs to
    that day. A line without a live ref is dropped. A line with a health value is dropped (`numericHealthIn`). Code renders the
    markdown.
  - **Read:** never injected whole. A third recall leg (`journal_recall`, FTS5 over `body_md`) joins `recallForTurn`. A
    `read_journal(day)` tool gives the model a page on demand. "What did I do last Tuesday" is answered from the journal, not
    from raw messages.
  - **Forget:** derived memory, so a day page carrying a held topic has that line deleted at once, in the forget's transaction.
    The page is rewritten from the redacted inputs on the next nightly run. Lines whose refs were all purged are deleted.

### 3. Long-term: claims, the *About you* notebook, the constellation

**Claims (canonical, unchanged).** One row per fact, with kind, source (`stated`, `confirmed` or `inferred`), origin, `source_ref`,
supersede chain and aliases. They are the unit of provenance, confirm, correct and forget. Their writers are as today, plus the
welcome build (inferred, non-owner). "Spots" become **notes** in the UI: a note is a claim.

**About you (`notebook_sections`, new, derived).**
- **Shape:** `(section TEXT PRIMARY KEY, body_md TEXT, claim_ids_json TEXT, compiled_at, version)`. The sections are fixed:
  - *Who you are*;
  - *Work*;
  - *People*;
  - *Rhythm and health* (patterns, never values);
  - *Interests*;
  - *How you like Waldo to work*;
  - *Waldo's read, not yet confirmed*.
- **One writer, the compiler.** One structured call reads the live claims and the current page, and returns
  `{ sections: [{ section, lines: [{ text, claim_ids[] }] }] }`. Code admits a line only when every cited claim is live and not
  held, and the text clears the barrier. It sends a line to *Waldo's read* when any cited claim is inferred or non-owner, and
  drops a line with a health value. It caps each section and the whole page (4,000 characters), then renders the markdown.
  The model decides what matters and how to say it. Code holds provenance, health and size.
- **When it compiles:** debounced, 2 minutes after a claim change, and also nightly and at the end of the welcome build. It is
  not inside a turn, and no compile output is written during a turn.
- **Pins:** an owner pin (M-8) says that claim must appear. The compiler is told so, and code checks that each pinned claim is
  cited. A pin that does not fit is reported, never dropped silently.
- **Every turn:** `turnMemoryPrompt` renders *About you* in place of the two pinned blocks once v2 lands, within the same 4,000
  characters.
  - The header carries a usage meter (`About you · 3,140 / 4,000`), as Hermes's does.
  - The page changes only when it compiles, so it stays stable for prompt caching between compiles. Unlike Hermes's
    session-frozen snapshot, it does not go stale over a weeks-long chat. Each line carries its claim ids (`[c12,c40]`), so the model can correct exactly what it reads with
  `remember(replaces_id)`. That is the claim-id-on-the-line form that exists today.
- **Owner edits:** the app or console shows each line with its cited claims. *Edit line* replaces the one cited claim
  (`claim.edit`, M-8), or adds an owner-stated claim and supersedes the cited ones. *Confirm* owner-grounds them. *Forget*
  forgets them. Then the page recompiles. The owner never edits a free-form markdown file, so no second truth can appear.
- **Forget:** deleting a claim deletes every line that cites it, in the forget's transaction. The page is not "redacted",
  because a line is derived and is deleted (ADR-0085). The next compile rewrites the section from what is left.

**Constellation (unchanged storage; it becomes the visual).** Nodes and edges interpret claims (nightly promotion, plus the
welcome build). The app's Constellation screen is the map of long-term memory. Chat reads nodes through *About you* (a node's
label can be a line, citing the node's supports). This replaces the welcome note's separate `<owner_constellation>` block once
v2 lands. Until then, that block is the bridge.

### 4. Procedural: how Waldo works for this person

- **Skills:** the existing `skills` table (`body_markdown`) with its existing review path. v2 adds no new procedural store.
- **The owner's preferences about Waldo** ("drafts short, no exclamation marks", "never book before 10") are preference claims,
  rendered in *How you like Waldo to work*.
- **Waldo's own instructions** (voice, soul, behaviour) stay protected, reviewed assets. The model never edits them.

## Health in memory, and the per-turn summary (ADR-0081 amendment draft)

- **Persisted:** nothing numeric about health, in any DO table, notebook, journal, node or trace. These are patterns in words:
  "late weekend sleeper", "recovers slowly after travel".
- **Per-turn summary (new destination):** when health sharing is live (`storage_compute` and `model_processing` granted for a
  source), each owner turn's context gets a compact `<health_today>` block, of at most 600 characters. It holds the latest
  night's sleep, recovery and form scores with their bands, resting HR and HRV against the owner's own 14-day baseline, and
  freshness. It is read live from Supabase at turn start through the signed series and scores read, and it is never stored.
  - **Why:** the owner wants Waldo to reason with real numbers on every turn. Today the model must call `get_health` first,
    and often does not.
  - **Rules:**
    - it is untainted turn context, not the system prompt;
    - the reply's trace text replaces the block with `[health summary withheld]` before export, whatever `captureText` is
      (a trace-privacy rule plus a test);
    - it is omitted when consent is not live, or when the read is stale past 72 hours. "No data" is said in words.
  - **Amendment draft:** in the ADR draft, section *ADR-0081 destination amendment*.

## Recall: is semantic recall in v2?

**Recommendation:** not in v2's first cut. It joins as v2.1, behind an evaluation gate. Today's recall is keyword FTS over claims
and episodes, with model-written aliases (`cleanAliases`) as the synonym bridge. v2 adds the journal leg and the *About you*
page, which carries most "who is this person" context on every turn without any search.

When to add embeddings: when the memory eval (golden cases for Recall@K and paraphrase queries) shows FTS plus aliases missing
more than an agreed share. The design is ready for that:
- vectors would sit in a DO SQLite table next to their row, so a forget deletes them in the same transaction;
- they would be computed by Workers AI, so the text stays with Cloudflare;
- search would be a brute-force scan, which is cheap at one owner's few thousand rows;
- results would be fused with BM25 by reciprocal rank.

The [appendix](#appendix-reference-systems-verified) covers the platform facts this rests on.

## Persistence (ADR scope)

- **New:** `notebook_sections`, `journal_days` (with the `journal_recall` FTS5), and `welcome_builds` (from the welcome note).
- **Removed, in a contract step after an inventory:** `memory_blocks`, `memory_inbox` and `patrol_log`. They have no writer
  (verified), but each still sits in the forget inventory, the held-rows diagnostic and the DO schema. The removal follows the
  cleanup rule in CLAUDE.md: inventory every reference, drop it from the forget lists, then the `DROP TABLE`. It goes in its own PR.
- **Forget inventory:** both new tables join it as derived stores whose lines are deleted.

## Build order (each step its own PR, red tests first)

1. **Welcome constellation** (already designed): ships in the cohort deploy with its bridge block.
2. **About you compiler plus every-turn rendering:** replaces the pinned blocks, adds `claim.confirm` and `claim.forget`, and the
   `notebook` view.
3. **Journal:** the nightly writer, the recall leg, `read_journal`, and the `journal` views.
4. **Per-turn health summary:** after the ADR-0081 amendment is accepted.
5. **Dead-schema removal:** after its inventory.
6. **v2.1 semantic recall:** behind the eval gate.

Tests per step, mirroring the welcome note's table:
- one writer;
- refs live, and a line without a live ref dropped;
- no health value persisted;
- forget deletes lines and the page recompiles without them;
- the app view's valid and invalid pairs;
- a chat turn carries the page within budget;
- the trace export withholds `<health_today>`.

## Appendix: reference systems (verified)

Read on 25 Oct 2026 at pinned SHAs or official docs. Two research passes did the reading. The rows marked ✓ were checked by hand
at the cited lines.

**Hermes Agent** (`NousResearch/hermes-agent@7e157789`)

- ✓ `MEMORY.md` is capped at 2,200 characters and `USER.md` at 1,375 (`tools/memory_tool_store.py:188`). Both live in
  `~/.hermes/memories/`.
- ✓ Both are frozen into the system prompt at load, to keep the prompt cache. Writes made during a session reach disk, not
  the prompt (`tools/memory_tool_store.py:224-255`). Load-time threat hits are replaced by `[BLOCKED: …]` in the snapshot only.
- The writer is one `memory` tool, with `target: memory|user` and atomic `add|patch|remove` batches (`tools/memory_tool.py:373-`).
- At the cap, the tool fails and returns the entries, and the model must consolidate. There is no automatic pruning.
- Background reviews stage removals for the user's approval.
- Skills are `SKILL.md` files. The prompt lists their names, and the model loads one with `skill_view`.
- Session search is FTS5 over messages (`hermes_state_fts.py`), as a tool, with no model call inside it.

**OpenClaw** (`openclaw/openclaw@bbe212f9`)

- `AGENTS.md`, `SOUL.md`, `USER.md` and `MEMORY.md` are injected every turn: at most 20k characters per file and 60k in total.
- Daily `memory/YYYY-MM-DD.md` notes are search-only. Today's and yesterday's load on `/new`.
- ✓ Hybrid search weights vectors 0.7 and text 0.3, with a candidate multiplier of 4, MMR λ 0.7 and a 30-day temporal decay
  (`src/agents/memory-search.ts:124-129`).
- ✓ Chunks are 400 tokens with an 80-token overlap (`:212`).
- The store is per-agent SQLite with FTS5. sqlite-vec is optional.
- Chunk provenance (`owner|agent|untrusted|system`) lives in SQLite, not in the markdown.
- Forget is an owner CLI that works by lineage, and it does not cover free-form file edits.
- A silent, append-only memory flush runs before compaction.

**Claude Code and the Claude API memory tool** (code.claude.com/docs/en/memory; platform.claude.com memory-tool docs)

- CLAUDE.md loads in layers: policy, user, project, then local.
- Auto memory sits in `~/.claude/projects/<project>/memory/`, with a MEMORY.md index. Its first 200 lines or 25 KB load
  every session, and topic files are read on demand.
- The API's `memory_20250818` tool offers `view`, `create`, `str_replace`, `insert`, `delete` and `rename` over a `/memories`
  path that the client backs with its own storage. That storage can be database rows.

**Cloudflare** (developers.cloudflare.com/durable-objects/api/sqlite-storage-api; /durable-objects/platform/limits;
/agents/runtime/lifecycle/sessions; `cloudflare/agents@321814b6`)

- FTS5 is supported in DO SQLite.
- Limits: 10 GB per object (paid), 2 MB per row, string or BLOB, and a 100 KB SQL statement.
- The Session API (experimental) offers token-budgeted context blocks and an FTS5 search provider
  (`packages/agents/src/context/search.ts:39-82`). It has no vectors.
- Loading sqlite-vec or other extensions is not documented. That is unverified, so v2 assumes no.
- Workers AI embeddings: `bge-small-en-v1.5` (384 dimensions), `bge-base-en-v1.5` (768), `bge-large-en-v1.5` (1024).
- Vectorize: at most 1,536 dimensions.

**Why semantic recall waits (the trade-off).** OpenClaw defaults to vector-weighted hybrid search, so the field leans toward
vectors. Waldo's corpus per owner is small, though, and mostly short claims with model-written aliases. *About you* puts the
person on every turn without any search. Embedding health-adjacent text is a further model egress to justify. v2 therefore
measures first:
- the memory eval (MEMORY_ROADMAP stage 13): paraphrase queries, Recall@K;
- then BLOB vectors in DO SQLite, scanned brute-force and fused with BM25 by reciprocal rank;
- a forget deletes the vector in the same transaction.

If the owner wants vectors at once, that path is ready to build. It costs one Workers AI call per new claim or journal line.
